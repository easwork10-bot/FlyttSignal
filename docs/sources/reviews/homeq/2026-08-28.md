# HomeQ — public Uppsala search and partner boundary

## Decision

HomeQ has two distinct interfaces and they must not share one access decision:

1. `public-uppsala-search`: anonymous and active for bounded live development collection.
2. `authenticated-api`: future partner route; remains `WAIT_PARTNER` until listing-read scope and use terms are confirmed.

## Public search verification

The user-provided Uppsala search opened without an account. On 2026-08-29 its public page used an anonymous `POST /api/v3/search` request and returned 26 Uppsala cards: 24 individual listings and two project cards. A project-filtered request returned 29 stable individual ads for Klacken and zero for Årsta Park. Project metadata remains separate from listing evidence.

Individual cards exposed canonical-looking URLs and numeric HomeQ identifiers. Anonymous detail pages exposed non-personal listing facts including address, landlord, rent, rooms, area, move-in date, publication date and HomeQ ID. Three objects were verified:

The fixture remains as deterministic parser evidence. The separate live source pages through the bounded public search, follows only individual `/lagenhet/{id}` links and reads landlord identity plus minimal facts from each public page's `__NEXT_DATA__`. It limits concurrency to four, caps the search at 100 cards and excludes descriptions, images, floor plans, applicant data and paid/private fields.

On 2026-08-29 the public web application was rechecked against its deployed search module. The
selected Uppsala shape is converted to map bounds; the anonymous API request itself uses
`geo_bounds`, `zoom`, `page` and `amount`. The visible page reported 53 homes and 26 paginated
top-level results. Adapter rule `homeq-public-search-v2` reconciled the same 26 cards as 24 ordinary
listings plus 29 active project ads and fetched 53 unique detail pages. Its first persisted run was
therefore `COMPLETE` for that exact configured search scope. It does not claim the whole Uppsala
municipality or all HomeQ inventory, and it still cannot infer removals in M3.1.

## Recurring-use gate

HomeQ's user terms were updated on 2026-04-10. They describe a limited licence to use the service and restrict changing, reproducing or copying the service and related content. The search is also rendered client-side and its supported data interface, rate limits and completeness semantics are not documented for this use.

The public interface is now used for controlled development collection at a three-hour interval. A supported feed or partner API remains preferable for long-term stability, lifecycle guarantees and published operating limits; it is an upgrade path rather than a blocker for present development.

The project-aware development run stored 53 individual Uppsala listings: 24 ordinary results plus 29 stable Klacken ads. It also stored two project records; Årsta Park correctly remained a zero-listing project. No project total is converted into synthetic listings, and no missing result can create a removal event.

M3.2 remains gated on at least three consecutive scheduled `COMPLETE` runs with rule version
`homeq-public-search-v2`, matching counts and no result-limit hit.
